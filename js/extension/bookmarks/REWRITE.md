# 书签管理器重写记录

本文档用于记录本次浏览器扩展重写的需求、设计取向、当前状态和后续进度，避免上下文丢失。

## 背景

当前目录 `js/extension/bookmarks` 原本是一个基于 WXT + Vue 的浏览器书签扩展。现已根据重写决策清理旧实现，改为先用标准 `Vite + Vue 3 + TypeScript` 工程实现稳定页面，再考虑接回浏览器扩展壳。

用户现有高频使用页面位于：

`R:\Files\Workspace\Mine\pages\docs\single\bookmarks`

现有页面是静态书签页，优点是简洁、信息密度高、长期使用不累，但缺点是书签数据固定，数千条内容无法方便动态维护。因此新扩展的目标是：基于浏览器原生书签实现同等甚至更好的高频入口，同时保留浏览器书签作为兜底数据源。

## 核心目标

- 浏览器书签是主数据源。
- 插件只保存额外数据，例如标签、备注、搜索 URL、个性化配置等。
- 所有新增、编辑、删除、移动、排序操作必须同步到浏览器书签。
- 浏览器书签在插件外发生变化时，插件需要实时监听并同步。
- 插件初始化或定时检查时，需要从浏览器书签重新校准数据。
- 当浏览器书签被删除时，对应的插件额外数据也要清理。
- 高频使用场景优先：快速搜索、快速打开、快速收藏。
- 整理能力要强：支持目录排序、书签排序、跨目录拖拽、明确拖拽反馈。

## 使用限制

沿用原需求中的限制：

- 只支持默认书签位置。
- 只允许一层目录。
- 只支持目录内书签。
- 不考虑移动端书签等特殊位置。
- 不需要兼容低版本浏览器。

## 当前实现状态

已分析现有实现，结论是：更适合重写，而不是继续在现有代码上小修。

主要问题：

- `manifest` 没有 `bookmarks` 权限。
- 代码中没有使用 `browser.bookmarks.*`。
- 当前实现把完整书签树存入 `browser.storage.local`。
- 新增、编辑、删除、移动、导入导出等操作都围绕插件本地 storage，而不是浏览器书签。
- 这与“浏览器书签为主、插件只存额外数据”的核心要求相反。
- 构建可以通过，但类型检查存在多处错误。
- 存在调试日志、未完成交互、运行时逻辑错误和 UI 体验问题。

因此后续采用：

**整体重写，保留可参考的工程技术选型和部分交互经验，不沿用现有业务核心。**

最新执行要求：

- `js/extension/bookmarks` 内旧代码不要继续保留和修补，已开始清理旧 `components`、`entrypoints`、`utils`、`prototype`、WXT 生成目录等内容。
- 新实现采用正常前端工程：`Node + Vite + Vue 3 + TypeScript`。
- 基础 UI 使用组件库，不再手写弹窗、菜单、表单、按钮状态等容易出小问题的基础交互。
- 当前组件库选型为 `Element Plus`，因为旧工程已有使用痕迹，适合快速落地稳定后台/工具型 UI。
- 拖拽使用专门工具库，不再手写 HTML5 拖拽细节；当前选型为 `vue-draggable-plus` + `SortableJS`。
- 瀑布流布局使用成熟库，不再手写 masonry；当前选型为 `Macy`。
- 工具能力使用 `@vueuse/core` 等工具库辅助键盘快捷键和状态交互。
- 所有需求、状态、实现决策必须同步写入本文档。
- 完成本轮整理和实现后，需要进行代码提交；提交信息使用简体中文。

## UI 方向

定位：紧凑型书签工作台。

### 不可退化要求

这些要求优先级高于组件库默认视觉和普通后台管理页习惯：

- 页面必须首先像高频使用的书签入口，而不是配置后台、管理表格或组件库 Demo。
- 浏览态必须服务“快速看见、快速搜索、快速打开”，不能长期展示低频管理元素。
- 主区域必须保持瀑布式/流式目录块布局，避免普通 grid 行对齐导致的信息断层和死板感。
- 目录块宽度、书签行高度、书签间距要接近旧页面的信息密度，但要比旧页面更清晰。
- 每个网站 favicon 是必要视觉锚点，不加图标边框。
- URL 是书签项的重要辅助信息，必须出现在标题下方，并形成接近旧页面“URL 顶到左侧”的自然分割感；不是只显示域名。
- URL 列表态允许 `ellipsis`，但完整 URL 数据不能丢，编辑/复制/提示中必须可取到完整地址。
- 左侧栏和管理控件不能抢书签标题、favicon、URL 的视觉焦点。
- 搜索是第一交互入口，打开页面默认聚焦搜索，并支持键盘选择结果、打开结果和搜索引擎搜索。
- 默认打开书签必须新标签打开。
- 整理目录时参考旧页面和禅道式布局拖拽：目录先收缩，拖拽过程中保持位置反馈清楚，结束后再重算瀑布流。
- 书签拖拽必须有明确目标反馈，不能靠浏览器原生拖拽的模糊状态。
- 基础 UI、弹窗、菜单、表单、拖拽行为优先使用成熟组件库/工具库，但组件库默认样式不能覆盖上述产品要求。

原型迭代记录：

- v1 覆盖了浏览态、整理态、拖拽反馈和 popup，但整体更像功能状态草图，成熟度不足。
- v1 的问题包括：右侧预览面板有设计稿批注感、主区域留白偏多、层级主要依赖边框、整体不够像真实长期使用产品。
- v2 调整为更完整的主页工作台：去掉右侧预览面板，保留高密度分组列表，强化搜索、favicon、目录标题、整理态控件和撤销反馈。
- v2 仍然偏硬，整体像后台管理表格，视觉节奏和美观度不足。
- v3 在 v2 基础上提升精致度：更柔和的背景层次、更自然的目录卡片阴影、更多真实数据密度、更细的状态色、更克制的整理态按钮。
- v3 仍有问题：不够接近最终使用版，存在一些日常不需要的常驻元素；侧栏字体和权重偏抢焦点；书签行间距偏紧；顶部搜索缺少设计完成度。
- v4 根据上述反馈调整：删除默认界面中的低频说明/状态元素，降低左侧栏字号和权重，提高书签标题字号与行距，给书签行增加轻分隔，重新设计顶部搜索为主控件。
- v4 主区域从普通网格改为瀑布式/流式布局：浏览态使用 Macy，接近旧页面使用感；整理目录时先收缩目录，拖拽结束后再重算布局，避免拖拽过程跳动。
- v4 滚动结构要求：Macy 布局容器不能同时作为滚动容器；外层 `.board-scroll` 负责固定高度和滚动，内层 `#board` 只负责 Macy 定位和内容高度。
- 后续实现应以 `prototype/v4` 为当前主要 UI 参考，v3 作为视觉层次参考，v2 作为结构参考，v1 仅作为状态覆盖参考。

设计原则：

- UI 克制，UX 增强。
- 默认界面服务“找书签、开书签”，管理能力不能干扰高频浏览。
- 实现上优先使用成熟组件库和工具库，避免手写基础 UI/拖拽造成大量小问题。
- 避免大面积装饰、渐变、玻璃拟态、大圆角和营销页风格。
- 保持高信息密度，但避免拥挤。
- 使用细边框、浅灰背景、低对比阴影、弱色彩点缀。
- 主内容区采用瀑布式/流式布局，避免普通 grid 的行对齐死板感。
- 书签项以行形式呈现，而不是厚重卡片。
- 每个网站的 favicon 是核心视觉锚点，必须展示；图标不使用额外边框，避免增加视觉噪声。
- URL 是重要辅助信息：保留完整 URL 数据，列表中按单行 `ellipsis` 展示，避免超长地址破坏版面；完整地址可通过标题提示、编辑或复制动作获取。
- 交互状态必须明确，尤其是拖拽、插入位置、无效区域、同步状态。

明确不要：

- 紫蓝渐变背景。
- hero 风标题。
- 大量卡片堆叠。
- 卡片套卡片。
- 大面积留白。
- 过度圆角。
- 玻璃拟态。
- 动画炫技。
- 影响信息获取效率的装饰。

可以使用：

- 等宽或半等宽字体。
- 小字号层级。
- 细分割线。
- 轻量 hover。
- 明确 focus 状态。
- 低饱和主色。
- 清晰的拖拽占位线。
- 整理模式下的状态条和操作栏。

## UX 模式

### 默认模式：浏览/搜索

- 顶部紧凑搜索栏，默认聚焦。
- 搜索栏支持普通书签过滤。
- 输入关键词并按 Enter 可用默认搜索引擎搜索。
- 输入 `! ` 或 `！ ` 进入特殊搜索模式。
- 主区域按目录分组展示书签。
- 标签筛选弱化展示，不抢主视觉。
- 编辑、删除、拖拽入口默认弱化，仅在 hover 或整理模式出现。

### 整理模式

整理模式需要显式进入。

进入后：

- 显示拖拽把手。
- 显示目录排序入口。
- 显示书签排序、跨目录拖拽反馈。
- 显示新增目录、新增书签、批量操作等管理入口。
- 顶部或侧边显示“整理中”状态。
- 管理操作完成后可退出整理模式，回到干净浏览界面。

### 拖拽反馈要求

拖拽是重点体验，需要明确反馈：

- 被拖动书签半透明。
- 原位置保留占位高度，避免列表跳动。
- 拖动预览只显示图标、标题和目标动作。
- 可放置目录需要明确高亮。
- 插入位置用清晰横线表示。
- 跨目录拖拽时目标目录需要进入接收状态。
- 无效区域显示 `not-allowed` 和弱红色反馈。
- 拖到列表顶部/底部时自动滚动。
- 放下后显示短暂成功反馈。
- 支持撤销最近一次移动/排序。
- 文件夹排序和书签排序的视觉反馈要区分。

## 数据架构方向

### 浏览器书签数据

使用浏览器原生 API：

- `browser.bookmarks.getTree`
- `browser.bookmarks.create`
- `browser.bookmarks.update`
- `browser.bookmarks.remove`
- `browser.bookmarks.removeTree`
- `browser.bookmarks.move`
- `browser.bookmarks.onCreated`
- `browser.bookmarks.onChanged`
- `browser.bookmarks.onRemoved`
- `browser.bookmarks.onMoved`

需要在 manifest 中添加 `bookmarks` 权限。

### 插件额外数据

插件 storage 只保存额外数据，不保存完整书签树。

建议结构：

```ts
type BookmarkExtra = {
  bookmarkId: string;
  tags: string[];
  description?: string;
  searchUrl?: string;
  faviconOverride?: string;
  updatedAt: number;
};
```

目录可根据需要保存额外展示配置，但不要复制浏览器书签目录树。

### 视图模型

页面展示时，从浏览器书签树 + 插件额外数据合成视图模型：

```ts
type BookmarkView = BrowserBookmark & BookmarkExtra;
type FolderView = {
  id: string;
  title: string;
  bookmarks: BookmarkView[];
};
```
