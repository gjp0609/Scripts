# Histories 第一阶段需求基线

更新日期：2026-08-14

## 1. 产品目标

第一阶段交付一个可以长期保存浏览历史、汇总多个 HTU 历史库并进行快速子串搜索的 Chrome/Firefox 扩展。

优先级顺序固定为：

1. 数据不丢失。
2. 应记录的访问尽量不遗漏。
3. 同一次访问不因多个采集通道而重复写入。
4. 多个 HTU 文件可以安全合并且重复导入结果不变。
5. 搜索和分页在大数据量下保持可用速度。

搜索索引、页面状态和统计信息都是可重建数据；访问记录库是唯一事实来源。

## 2. 第一阶段范围

### 2.1 历史记录

- 首次运行时读取浏览器中已经存在的全部可访问历史。
- 运行期间监听新的访问事件，尽快写入本地历史库。
- 每次打开历史页面时执行增量补偿扫描，补齐后台休眠、扩展关闭或监听丢失期间的访问。
- 后续可增加低频定时补偿扫描，但定时导出备份不在第一阶段。
- 实时采集和增量补偿只更新受影响的页面与搜索索引；日常启动不得重复全量建立搜索索引。
- 全量索引重建只用于首次大批量导入、索引格式升级、索引损坏或用户明确触发的修复。
- FTS 只在出现新 URL 或可搜索文本变化时更新；已有 URL 的新增访问如果没有改变标题，不得重写 FTS。
- 访问次数、最近访问时间、时间范围过滤和时间排序由 IndexedDB 主数据及索引负责，不写入 FTS 作为权威状态。
- 未进入最新完整快照的 dirty page 必须持久记录；启动时加载旧快照并批量重放，达到阈值或空闲时再生成完整 checkpoint。
- 不监听、不保存也不执行浏览器历史删除动作。浏览器侧删除或自动过期不能删除 Histories 已保存的访问。
- `data:image/...` 数据图片 URL 不写入访问主库或搜索索引，避免保存大段无实际访问意义的内联图片数据；同步和导入结果只记录被忽略的数量，不记录其完整 URL。
- 同步游标只在对应数据已经成功持久化后推进。
- Chrome MV3 后台被回收、浏览器异常退出或任务中断后，再次运行必须能够安全补偿。

实时监听与补偿扫描是优先方案。如果真实浏览器压力测试证明双通道无法可靠去重或显著降低稳定性，可以退回 HTU 式的“打开页面时增量扫描”模式；退回前必须保留测试证据和结论。

### 2.2 两层去重规则

系统必须区分两种不同含义的去重，不能混为一个开关。

采集幂等去重：

- 用于实时事件、补偿扫描、任务重试和重复导入再次发现同一次访问的情况。
- 始终启用，用户不能关闭。
- 同一次访问无论被多少采集通道发现，都只能形成一条规范访问记录。
- HTU 数据优先按精确 URL 与访问时间兼容去重；浏览器事件应同时利用可获得的 `visitId`、`referringVisitId`、访问时间和 URL，并允许补偿扫描匹配实时事件。
- 每条规范访问可以关联多个来源记录，以便审计为什么它被判断为重复。

频繁访问抑制：

- 用于主动忽略同一精确 URL 在指定时间间隔内发生的多个不同访问，行为参考 HTU。
- 这是用户配置，不是采集幂等的一部分。
- 默认阈值为 `2.0` 秒；设置为 `0` 时不抑制不同访问。
- 应先完成采集幂等判断，再按访问时间顺序应用频繁访问抑制。
- 不同 URL 不得因该设置相互影响。
- 只作用于从浏览器历史 API 实时或补偿采集的数据，不得过滤 HTU 文件中已经存在的访问行。

最终唯一键和跨浏览器来源模型需要通过真实 Chrome、Firefox、重复导入及事件/扫描交叉样本确定，不能只依赖内存中的任务 ID。

### 2.3 HTU 合并导入

- 支持 HTU 3 列、4 列和 8 列 TSV 格式，以及已经确认的旧 Windows epoch 和 `U<unix_ms>` 时间格式。
- 支持依次选择和导入多个浏览器、多个时间点生成的 HTU 文件。
- 新导入必须与现有历史合并，禁止清空或覆盖已经成功导入的数据。
- 同一文件重复导入、存在重叠时间段的备份重复导入，结果必须保持幂等。
- 不重复的访问、每次访问的标题、transition 和时间必须完整保留。
- HTU 文件中的 `data:image/...` 行按全局排除规则忽略，并计入导入报告；除此之外不得用频繁访问阈值过滤导入行。
- 保存导入批次、源文件哈希、导入时间、源标签、输入行数、新增数、重复数、忽略数和错误数。
- 文件必须先完成结构校验，再进入合并阶段；失败或取消不能留下半个可见导入结果。
- 合并和重建索引不是高频操作，允许耗时较长，但必须显示阶段、进度、结果并支持失败后安全重试。

多文件的推荐处理顺序：

```text
解析并校验所有输入
  -> 写入隔离的导入批次
  -> 全量排序和采集幂等去重
  -> 原子提交正式历史数据
  -> 一次性重建搜索索引
```

### 2.4 导出与恢复

第一阶段提供两类手工导出：

- 原生完整备份：用于 Histories 的完整恢复，保存访问字段、来源、导入批次、格式版本和完整性校验信息。
- HTU 兼容导出：至少支持 HTU 4 列归档 TSV，便于回退和数据交换。

原生备份格式可以使用 ZIP 容器，内部包含版本化清单、分块数据和 SHA-256 校验。具体编码在实现前单独设计，但必须满足：

- 大文件不依赖在页面和 worker 之间复制一个完整字符串。
- 导出后导入空库，页面数、访问数、关键字段和来源信息完全一致。
- 导出失败或取消不会影响历史主库。
- 未实现定时自动备份不妨碍手工完整备份。

### 2.5 搜索与分页

- 搜索字段：标题、原始 URL、可安全解码后的 URL。
- 最短关键词：标准化后至少 3 个字符。
- 匹配语义：大小写归一化后的连续子串匹配，不要求完整单词或 HTU 式完整分词。
- 时间条件：可选起始时间、结束时间或完整时间范围。
- 组合查询：模糊子串与访问时间范围必须同时生效。
- 结果语义：以访问记录为时间依据；同一页面可以展示匹配时间范围内的访问次数和最近一次匹配时间。
- 排序：默认按匹配访问时间倒序，使用稳定的次级排序键，保证翻页时不重复、不跳项。
- 分页：必须在存储和查询层分页，不能先加载全部结果再由页面切片。
- 搜索索引缺失或损坏时，历史数据仍可读取并可重建索引。

必须针对 `887,561` 条访问、`384,065` 个 URL 的外部备份规模测量：

- 无时间范围的第一页及连续翻页。
- 窄时间范围和宽时间范围。
- 高命中、低命中和零命中关键词。
- 第 1 页、中间页和深分页。
- 索引加载后常见查询目标低于 `100 ms`。
- 分页性能必须记录实际数据，之后再决定使用游标分页还是允许有限的 offset 分页。

## 3. 第一阶段界面

在第一阶段已纳入的功能范围内，页面结构、控件位置和交互与 HTU 保持一致，不做独立的视觉重设计。统计、高级筛选器等未纳入功能不显示，不要求为了视觉一致保留无效占位。

历史页：

- 扩展启动后默认进入历史页。
- 提供关键词、起始时间、结束时间、搜索、翻页和同步状态。
- 时间显示默认使用 24 小时制。
- 长任务提供明确的运行、成功、失败和可重试状态。

设置页只保留：

- 导入
- 导出
- 存储统计
- 默认启动页，第一阶段固定为历史页或仅展示该值
- 时间显示，默认 24 小时制
- 同步历史的频繁访问忽略秒数，默认 `2.0`

存储统计仅包括页面数、访问数、数据占用、搜索索引占用、索引状态、最近同步和任务状态，不包含访问趋势分析。

## 4. 明确不做

- 统计分析、趋势图表和排行榜。
- 定时自动备份。
- 除时间范围外的 HTU 高级筛选器。
- 浏览器历史删除同步、删除标记或删除状态。
- 云同步或远程数据上传。
- 新标签页、二维码、翻译和其他无关工具。
- 1～2 字符子串搜索；后续如有需要另行设计和验证。

## 5. 稳定性验收

以下条件全部满足后，第一阶段才可视为可长期使用：

- 全量扫描、实时监听和补偿扫描覆盖的访问集合符合预期。
- 同一访问由事件与扫描重复发现时只保存一条。
- 使用默认频繁访问阈值和阈值 `0` 时，结果分别符合定义。
- 同一个 HTU 文件连续导入两次，第二次新增访问数为零。
- 多个存在重叠数据的 HTU 文件按不同顺序导入，最终规范访问集合一致。
- 导入、同步、索引重建过程中关闭页面、终止后台或重启浏览器，主库不损坏且任务可补偿或安全重试。
- 删除搜索快照后可以从主库重建，重建前后查询结果一致。
- 浏览器删除原始历史后，Histories 中已保存的访问仍然存在。
- 原生备份完成空库往返恢复，并通过计数、字段和校验值比对。
- Chrome 和 Firefox 均完成真实扩展环境的完整流程测试。

## 6. 已确认与待验证

已确认：

- 最短搜索关键词为 3 个字符。
- 第一阶段搜索为连续子串加时间范围。
- 默认启动页面为历史页，时间显示默认 24 小时制。
- 只记录访问，不响应浏览器历史删除。
- 多 HTU 文件先合并去重，再统一建立搜索索引。
- 频繁访问抑制只用于浏览器同步，不过滤 HTU 导入数据。
- 浏览器采集和 HTU 导入都排除 `data:image/...` 数据图片 URL。
- 真实 `900,177` 条访问规模已验证增量 FTS 可行：最近 7 天 `2,264` 条访问的推荐策略 dirty replay 约 `407 ms`，逐条更新 P95 约 `1.12 ms`；完整快照保存约 `2.50 s`，因此只能低频 checkpoint，不能每次访问保存。
- 统计分析和定时备份推迟到后续阶段。

需要通过实现和测试确定：

- 实时监听加补偿扫描能否在 Chrome/Firefox MV3 生命周期下稳定工作；不满足则退回页面打开时增量扫描。
- 浏览器事件与 HTU 文件之间最终采用哪些字段形成规范访问身份。
- 时间倒序分页的最佳查询计划和深分页上限。
- 约 `558 MB` 搜索快照在 Chrome/Firefox 扩展上下文中的实际配额和恢复行为。
- 原生完整备份的最终容器与分块编码。
